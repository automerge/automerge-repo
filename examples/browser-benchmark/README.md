# Browser responsiveness benchmark (experimental)

Real browser, Repo, IndexedDB, and (for `poc` and `subductionjs`) Subduction. No server/network connection. The `main` baseline uses its legacy IndexedDB adapter instead of Subduction; comparisons include storage architecture differences. This is a foundation, not a performance gate.

## Run

From the workspace root:

```sh
pnpm install
pnpm --filter @automerge/automerge-repo build
pnpm --filter @automerge/automerge-repo-subduction build
pnpm bench:fixtures
pnpm bench:browser --target=poc
```

The browser page shows progress, per-size results and edit updates live. Download raw JSON using the button. Add `?smoke` for 10 loads and 30 edits; add `?reseed` to explicitly replace the prepared store. Normal runs load the first 10, 100, 500 and 1,000 URLs from one store, opening and closing a **new Repo** for each size. One manifest of deterministic `.automerge` files is generated by plain Automerge (32 strings, 51 changes per document, fixed actors and timestamps), then imported _via Repo_ into IndexedDB once per target. The seed is reused across runs. Seeding is not timed as part of loading. After a new seed, the page reloads **once before measurement** to release its construction-time JS/WASM state. There is no reload between load sizes. If the fixture manifest changes, the page refuses to reuse the existing seed: add `?reseed`.

For repeatable headless results, install Playwright Chromium (`pnpm --filter @automerge/automerge-repo-browser-benchmark exec playwright install chromium`) if it is not already present:

```sh
pnpm --filter @automerge/automerge-repo-browser-benchmark automate --smoke --runs=2
pnpm bench:prepare main=base/main:legacy
pnpm bench:prepare subductionjs=base/subductionjs:subductionjs
pnpm bench:compare --smoke --runs=3
pnpm bench:compare --runs=3
```

Comparison defaults to `main subductionjs poc`, in that order each round. `main` means `base/main`, not the npm dist-tag. Other branches: `pnpm bench:prepare speed=base/subductionjs-speed:subductionjs`, then `pnpm bench:browser --target=speed` or `pnpm bench:compare --runs=3 main speed poc`. Targets use detached worktrees with their own frozen-lockfile installs in `~/Library/Caches/automerge-repo-bench/` on macOS or `$XDG_CACHE_HOME/automerge-repo-bench/` on Linux. Override with `BENCH_CACHE_DIR`. Prepared names and commit SHAs live in that cache's `index.json`. Worktree commits can move; prepare the name again to update it. Do not edit the managed worktrees. Browser profiles are kept under the ignored `results/profiles/<target>/`. Raw reports and comparisons are ignored under `results/`, visible to local agents.

`--reseed` replaces the target's saved data; it is **not** required for repeat runs. `--edits=1000` is a diagnostic partial workload and marks the report `custom`, not a full benchmark. Each edit run uses a new database. Automation tries to remove it after closing the benchmark page, as older Subduction workers can keep IndexedDB connections open until then. Manual-browser edit databases can be deleted in DevTools.

## Measurements

Loads record the elapsed time from submitting all `find()` requests until each URL becomes ready, plus frame gaps and supported Long Tasks. They verify the final count on every document and record IndexedDB key count/byte totals before and after (a **coarse** mutation check, not a content hash). New Repo instances share the same page/WASM runtime, browser disk caches and store; there is no per-size reload, disk-cold guarantee or network benchmark. `jsHeapBytes` is browser-dependent; `wasmBytes` is `null` because the libraries expose no comparable WASM memory counter.

Edits are paced one per animation frame. `callMs` times synchronous `change()` execution including its immediate change event and the tiny DOM sequence update; frame gaps and Long Tasks reflect responsiveness. `durableMs` is available only on `poc` (the other handles return `void`, so it is `null`). After 5,000 edits the harness calls `flush()`, reopens a Repo, and checks the final state. If draining takes more than two minutes, raw edit-call and load samples are saved with `verified: false` and `drainMs: null`; do **not** interpret this as a durable-edit success. The timed-out edit database is not reused. Comparison reports retain valid load/edit-call comparisons but mark drain comparisons incomplete.

Imports run after loads, each into a fresh database that is deleted afterwards, so they are always timed (seeding is not). Three classes: `small` imports 20 of the 51-change load fixtures (52 records each); `medium` and `large` import `import-medium.automerge` (1,000 changes, 388 records) and `import-large.automerge` (2,200 changes, 762 records) three times each. These come from `fixtures/v1/imports.json`, a separate manifest so the load manifest hash and prepared store are unchanged. The shapes are pinned by the record count Automerge produces after save/reload, which is what `import()` submits as one batch; the count is not monotonic in changes and depends on the edited content, so `generate.mjs` fails if it drifts. `importMs` runs until `import()` resolves and `flushMs` until the following `flush()` resolves (older adapters return from import before persisting); `verified` means a reopen read the final count back. A rejected import is recorded as a failed sample with its error rather than aborting the run; a class with any failure compares as `null`. Heap samples are before/after, not peak.

Results contain fixture hash, exact ref SHA, adapter, browser version, dirty flag, seed reuse/time, raw samples and summary medians/ranges relative to `main`. For a meaningful conclusion run three rounds, rather than judging a single warm-browser run. The edit workload does not yet overlap loads; add that as a separate scenario later.

## Seeding investigation

`pnpm --filter @automerge/automerge-repo-browser-benchmark diagnose` writes `results/seed-diagnosis.json` from a Node `MemoryByteStore` experiment (1 vs 10 documents, 1/10/51/80 changes). With 10 documents, 1 change caused ~120 loads and 70 listings; 51 changes caused ~12,000-15,000 loads and ~500 listings; 80 changes caused ~28,000-35,000 loads and ~700-850 listings. Browser seeding 10 fixtures (51 changes each) caused 10,831 IndexedDB loads, 443 listings and 403 saves; the reads and listings accounted for ~4.5s of a ~6.8s seed. Counts vary with fragmentation and backend IDs, but the growth within documents is clear. `StorageBridge.savePrepared()` re-snapshots the whole stored tree for every record, and `SubductionBackend.storeRecords()` also reads the tree before and after a batch. This explains much of the slow seed without blaming fixture generation (plain Automerge completes quickly). Compare read counts before trying to optimize; this harness does not change backend behavior. Importing >128 records in one document can hit the backend's batch limit, so the diagnostic stops at 80 changes. A Chrome CPU profile remains useful for distinguishing JavaScript decoding, native work, and IndexedDB transaction overhead.
